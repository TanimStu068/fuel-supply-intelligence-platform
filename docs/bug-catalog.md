# Bug Catalog

Every defect found during the seven-day build of the Fuel Supply Intelligence &
Resilience Platform, with the day it was found, what it looked like, why it
happened, how it was caught, and the test that now pins it.

**Sources.** [`docs/progress/day1.md`](progress/day1.md) …
[`day7.md`](progress/day7.md),
[`docs/resilience-report.md`](resilience-report.md),
[`docs/load-test-report.md`](load-test-report.md),
[`docs/model-evaluation.md`](model-evaluation.md),
[`docs/fault-tests.md`](fault-tests.md), and the `fix`/`revert`/`perf`
commits in the git history. Every number and date below is taken from one of
those files; nothing here is estimated.

**How to read the "Test that pins it" column.** `file::test name` means the
regression test that exists in the repository today and fails without the fix.
`—` means no dedicated regression test exists; the defect is pinned only by a
script, a drill or a document. Those are listed honestly rather than being
given a test name that does not exist.

**Scope.** This is a catalogue of defects in **our** code. The ten simulator
discrepancies in [`docs/simulator-notes.md`](simulator-notes.md) and the eight
simulator findings in [`docs/fault-tests.md`](fault-tests.md) are properties of
the organizer's image, not bugs we wrote; they are referenced only where they
caused one of our defects.

## 2. Patterns

Seventy defects, and they are not seventy unrelated accidents. Six patterns account for most of them.

### Pattern A — Code that exists but is never called

The single most expensive pattern. A method that exists, is correct, and is only reachable from a test looks **identical** to a method that works. The defect is invisible to every unit test, because the test calls the method directly.

| ID | The code that was never called |
|---|---|
| B7 | `_ingest_demand_history` — existed, was never called from the sync loop |
| B8 | `_raise_alerts` — existed, was never called from the sync loop |
| B51 | `ML_KILL_SWITCH_FALLBACKS.inc()` — the counter was defined, never incremented |

**How they were found.** By looking at the **database**, not at the return value. The demand table was empty and the alerts table was empty while the unit suite was green.

**The lesson.** Assert on the *stored* state, not just on the return value. A function that is never called by the production path must have a test that goes through the production path.

### Pattern B — Silent failures: the system looked healthy while it was wrong

The most dangerous pattern, because every automated check passed.

| ID | What the system claimed | What was true |
|---|---|---|
| B2 | The dashboard was up and the API was reachable | The browser blocked every cross-origin request |
| B49 | `sse_connections_total` = 1, so the platform had a live event feed | The platform had been dropped from the bus and the stream was delivering nothing |
| B62 | `degraded: false`, `age_seconds: 0.2` — the data was fresh | The data belonged to a run that had ended |
| B51 | The kill-switch counter read zero | It was never incremented, so "zero" meant "never measured", not "never happened" |
| B64 | The extrapolation probe reported a confident −25.4 % | It was comparing the same builder against itself |
| B24 | The benchmark said the model lost | The baseline had been handed the answer it was asked to predict |

**The lesson.** "The process is running" is not evidence. The evidence is a number that a bug would have changed.

### Pattern C — Measurement bugs: the instrument, not the subject, was wrong

Five defects where the *measurement* was the defect. In each case the platform or the model was fine; the thing reading it was not.

| ID | The instrument | The defect |
|---|---|---|
| B45 | The health panel's p95 | The Prometheus histogram's buckets are cumulative counts; summing them gave a p95 of 1,000,000 s and a request count of 5.4 billion |
| B24 | The horizon benchmark | The baseline was read from the *end* of the window it was asked to predict |
| B26 | The evaluation harness | Stepping the simulator flat out measured the step rate, not the policy (0.763 vs 0.882 for the same code) |
| B58 | The load-test safety stop | Saturation was treated as a failure, so two of three workloads never ran |
| B64 | The extrapolation probe | Both arms ran the same builder, so the comparison was identical to the decimal |
| B68 | The horizon validator | The model had been fitted on the window it was scored against — the leaky score was −60.7 %, the honest score +3.7 % |

**The lesson.** A benchmark that flatters the incumbent is worse than no benchmark. A probe that cannot fail is not evidence.

### Pattern D — Resource leaks and unbounded growth

| ID | The leak | The symptom under load |
|---|---|---|
| B50 | The platform read the world on every SSE tick event — ~70 req/s against a 15-connection pool | The simulator answered 500 until it was restarted |
| B52 | The decision service's in-memory store had no bound | 3,000 recommendations and 22 MB, re-serialised every 5 s |
| B53 | The prediction-error aggregate read the whole table into Python | The container was OOM-killed nine times in a row at its 670 MB limit |
| B54 | The scoring window was unbounded | 760,809 rows pulled into memory every sync cycle |
| B47 | The recommendations page rendered every card | A 6 MB screenshot and an unusable page |

**The lesson.** Every collection that grows needs a bound, and every aggregate belongs in the database.

### Pattern E — Route shadowing and unreachable branches

| ID | The shape |
|---|---|
| B43 | `/api/simulation/crisis` registered after `/api/simulation/{action}` — FastAPI matched `crisis` as an action name |
| B28 | The one-step check returned early, making the horizon check — described in the source as "the decisive check" — unreachable dead code |
| B1 | A stale `__pycache__` entry masked a broken import; the module was never imported at test time |
| B29 | `SimulatorClient.instance()` did not exist; the real method is `get_instance()` |

**The lesson.** Registration order and early returns are both load-bearing. A branch the source calls "decisive" should have a test that proves it is reachable.

### Pattern F — Edits that were silently reverted

Day 4 records this explicitly: *"Several edits in this session were silently reverted by an external process — the tool reported success, and the file on disk did not have the change. Twice that produced a green test suite with broken code behind it."*

Two things came out of it:

* [`scripts/day4_verify_state.py`](../scripts/day4_verify_state.py) asserts the specific facts the implementation is supposed to hold, straight from the source files, so a reverted edit is caught before it reaches a commit.
* Every change is verified with `grep_search` after it is applied, not just after the tool says it succeeded.

B70 is a *deliberate* revert rather than an accidental one, but it belongs in the same family: a performance change that looked right and produced a wrong answer was reverted rather than left in.

### Pattern G — Duplicated rules that drift

| ID | The duplication |
|---|---|
| B38 | The optimizer and the fallback policy both implemented "lowest days-of-cover first" |
| B57 | The audit *page* and the audit *count* used different windows, so the count described a different set of rows than the entries beside it |

**The lesson.** One rule, one implementation. When two places compute the same thing, they will eventually disagree, and the disagreement will be read as a fact.

## 3. Eight deep dives

### 3.1 B24 — The benchmark handed the baseline the future

**Symptom.** The first evaluation run reported the learned model *worse* than the rule-based baseline: 159.2 L against 111.6 L over a 96-tick horizon. The platform did exactly what it was told — it fell back to the baseline and reported `worse_than_baseline`.

**Investigation.** Three causes were separated before any of them was fixed. (1) *The forecast design*: the forecast was recursive, so the prediction for tick T+1 became the lag for tick T+2, and over 96 steps every error fed back into the next. (2) *The data*: a simulator reset left the old run's tick 1 next to the new run's tick 1, and the forecaster learned from a discontinuity that never happened. (3) *The benchmark*: the horizon validator took the baseline's multiplier from `points[-12:]` — the **end** of the window being predicted. The baseline was being handed the answer it was asked to predict, while the model only ever saw the history before it.

**Fix.** The forecast became **anchored** — every step is predicted from the observed history, with the station's current level carried forward. The stored history is dropped when the clock goes backwards. The baseline now uses the history before the window, exactly like the model.

| Design | Horizon error | Baseline | Verdict |
|---|---|---|---|
| Recursive | 866 L | 110 L | baseline wins — the model was rejected |
| Anchored | 800 L | 1,262 L | learned wins by 37 % |
| **Anchored + honest benchmark** | **78.1 L** | 118.1 L | learned wins by **34 %** |

**Lesson.** The platform behaved correctly on a dishonest result — it threw away a good model because the comparison was rigged. A benchmark that flatters the incumbent is worse than no benchmark, because it does not merely mislead a human reader: it makes the platform discard something good and believe it is being careful.

### 3.2 B49 — The platform believed it had a live event feed

**Symptom.** With the simulator stopped, `sse_connections_total` stayed at **1** and `sse_reconnects_total` never moved, while the REST poller correctly went degraded. The platform was serving a dead world with a healthy-looking stream attached.

**Investigation.** Three independent causes, all of which had to be fixed before the platform could notice a dead simulator at all. (1) The reader *awaited* every full sync cycle triggered by a `simulation.tick` event; the simulator runs eight ticks a second and a cycle reads nine endpoints, so the reader read about **fifteen events per fifty seconds**. The simulator's queue is 200 deep and it **unsubscribes** a client whose queue overflows — so the platform was dropped from the bus entirely, while the stream stayed open, kept sending keepalives, and delivered nothing. (2) `httpx.Timeout(read=None)` means a socket whose far end has gone away produces neither data nor an error: the reader waits forever on a connection that will never answer. (3) The dead simulator's queue keeps delivering buffered events for minutes, each one resetting every read timeout — so *"bytes are still arriving"* proves nothing.

**Fix.** The refreshes are now *scheduled* rather than awaited, so the reader never stops reading. The read timeout is a bounded `SSE_READ_TIMEOUT` (30 s). And `_sse_stream_is_stale()` compares the stream's own tick against the independent REST view: if the REST view says the world has moved on and the stream has not, the stream is describing a world that no longer exists, and it is dropped after `SSE_STALE_GRACE` (45 s).

| | Before | After |
|---|---|---|
| SSE connections opened in 25 minutes | 17 | **1** |
| SSE events received | 15 per connection | **742 in 3 minutes** |
| Stale-stream drops on a *healthy* simulator | one every ~50 s | **0** |
| Time to notice a stopped simulator | never | **~40 s** |

**Lesson.** A live connection is not a live feed. The evidence that a stream is alive has to come from somewhere *other* than the stream — here, from an independent REST view of the same world.

### 3.3 B62 — The platform served a world that had ended

**Symptom.** `POST /admin/reset` starts the world again at tick 0. One second later the platform reported tick **892**, `degraded: false`, `age_seconds: 0.2`.

```text
=== BEFORE reset ===
{"tick":893,"sim_time":"2026-01-10T07:15:00"}
{"tick":892,"sim_time":"2026-01-10T07:00:00Z","degraded":false,"age_seconds":0.12}

=== POST /admin/reset ===
{"tick":0,"status":"PAUSED"}

=== IMMEDIATELY after (within 1s) ===
{"tick":892,"sim_time":"2026-01-10T07:00:00Z","degraded":false,"age_seconds":0.2}
```

**Investigation.** The age was technically true — the cache *was* refreshed 0.2 s ago — but it was refreshed with the numbers of a run that had ended. The platform was not stale. It was **wrong, and it looked fresh**. The platform's own history-wipe already handled the *database* half of a reset: it noticed the clock had gone backwards and dropped the stored demand history, so the forecaster would not read two runs as one series. The **cache** was never covered. The two halves of the same event were handled in two places, and only one of them remembered. A second bug hid inside the first: the event stream's tick tracker still said 892 after the reset, so the platform would have decided the stream was permanently stale and reconnected, for ever.

**Fix.** The invariant lives in `StateCache`: *the cache never serves a world that no longer exists.* A snapshot whose tick is behind the cached one means the world was reset. `SyncService.forget_the_previous_world()` drops the cached snapshot and resets the stream's tick tracker, so `/api/state` answers **503 "no simulator state available yet"** until the next cycle fetches the new world. The platform's own reset endpoints call it, so the window does not open at all when the platform does the resetting; and when the reset comes from **outside** — the simulator's own admin console, or the organizers' scripts — the simulator announces it on the stream (`event: simulator.notice`), and the platform now handles that notice by dropping the world and re-reading it.

| | Before | After |
|---|---|---|
| The state served one second after a reset | tick 892, `degraded: false`, age 0.2 s | **503, no state** |
| The state served two seconds after a reset | tick 892, `degraded: false` | **the new world** |
| A reset done from the simulator's own console | not noticed | **noticed within 2 s** |

**Lesson.** "How old is this data?" is the wrong question when the question is "is this data *about* the current world?". Freshness and relevance are different properties, and a platform that reports only the first will confidently serve the wrong thing.

### 3.4 B56 — A 500 on the query an operator is most likely to type

**Symptom.** `GET /api/audit?q=disrupted&entity_id=station-mirpur` returned HTTP 500. Every combination of a needle with an entity id answered 500; every other filter combination worked.

**Investigation.** A full-text search reads from a bounded subquery instead of the table, and every clause has to be rewritten against it — if a clause still points at the table, the query joins the two back together and the whole table is read again, which is the bug the subquery exists to prevent. The rewrite looked each column up **by name**. But not every clause *is* a column: the events trail's entity filter reaches into the JSON document — `parameters->>'entity_id'` — and an expression has no name to look up. It raised `KeyError: None` while the query was being **built**, so the endpoint never got as far as the database.

**Fix.** The fix uses SQLAlchemy's own `ClauseAdapter` instead of a hand-written lookup, and it adapts **whole clauses** rather than individual columns. The second half matters: a clause that still mentions the table is not merely untidy — SQLAlchemy adds the table to the `FROM` to satisfy it, and the query becomes a **cartesian product** between the window and the whole table. That is not a slow query, it is a wrong one: the decision trail's count took **147 seconds** that way. Building the clause first and adapting it after keeps every `WHERE` reference pointed at the window.

**Lesson.** A query-builder abstraction is only as good as its handling of the case it was not written for. Looking a thing up by name assumes the thing has a name; in a schema with JSON columns, it often does not.

### 3.5 B53 — The platform was OOM-killed nine times in a row

**Symptom.** The dashboard's read path saturated. The load test recorded a p99 of **30,029.78 ms** — which was the harness's own thirty-second timeout, meaning requests were not merely slow, they were not being answered at all. The backend container was killed and restarted **nine times** in a row, reaching its 670 MB limit exactly.

**Investigation.** The intelligence evaluation took **9.9 seconds of the 10.25-second cycle**. It was not the model — the engine evaluates the whole network in 36 ms. It was the **error metric**: after every cycle the platform read *every row* of `prediction_evaluations` into Python to compute a mean absolute error, and that table holds one row per station, per fuel, per tick — 928,005 rows.

**Fix.** Compute the aggregate in the database, where the data already is, and move the evaluation off the event loop into a worker thread so the API can answer while the forecast runs.

| Metric | Before | After | Change |
|---|---|---|---|
| Throughput | 41.75 req/s | **335.39 req/s** | **8.0×** |
| **p99** | **30,029.78 ms** | **286.13 ms** | **105× faster** |
| **Container memory (peak)** | **670 MB** (at the limit) | **102 MB** | 6.6× less |
| Error rate | 0.52% | **0.00%** | — |

**Lesson.** The fix is not "use more memory" — it is "never read the table". The "before" side is still in the repository behind `PREDICTION_ERROR_AGGREGATE_IN_DATABASE=false`, so the number can be re-measured rather than remembered.

### 3.6 B28 — Dead code in the place that mattered most

**Symptom.** The platform used the rule-based predictor for the whole run and reported `fallback_activations_total{reason="not_trained"} 272`. The source described the horizon check as *"the decisive check"*.

**Investigation.** Two checks decide whether the learned model is trusted: the one-step validation MAE, and the horizon MAE over the replay window. The code checked the one-step score **first** and returned as soon as it failed. That made the horizon check unreachable dead code. The effect was not subtle — one injected spike inside the validation split was enough to make the model look worse one step ahead, and the selector threw away a model that was winning the horizon by more than 2×:

```text
one-step:  model 0.0940 vs baseline 0.0601   <- the model loses here
horizon:   model 1,227 L vs baseline 2,729 L   <- the model wins by 2.2x
active:    baseline                           <- wrong
```

**Fix.** The horizon check now runs first, because it is the measure that matches how the model is *used*. The one-step score only decides when there is no horizon score to judge by.

**Lesson.** A comment saying a branch is decisive is not evidence that it is reachable. The measurement that decides must be the one the system is actually judged on — and it has to be *tested* as reachable, or it is a promise in a docstring.

### 3.7 B2 — Green by every automated check, broken in the judge's browser

**Symptom.** The dashboard showed **"Backend unreachable: Failed to fetch"** while the whole stack was up and green.

**Investigation.** Two independent faults, either of which alone was sufficient. The browser blocked the cross-origin call — the backend had no CORS middleware. And Vite inlines `import.meta.env` at build time, so the API URL was **frozen into the bundle** at image build time and could not be changed without a rebuild.

**Fix.** CORS was added to the backend. The frontend now resolves the API URL at **runtime** from `public/config.js`, which the container entrypoint rewrites from `API_BASE_URL` — so one image works against any backend address.

**Lesson.** "Does it compile" and "does it answer" are different questions, and neither of them is "does it work in a browser". This was the most valuable bug of Day 1 precisely because every automated check passed.

### 3.8 B64 — A probe that could not fail

**Symptom.** `scripts/extrapolation_probe.py` exists to compare two feature sets: the **absolute tick** the platform used to ship, and the **tick's position within the day** it ships now. It reported:

```text
absolute tick (as shipped)   model  176.9 L   baseline  237.2 L   diff -25.4%   wins 7/12
tick within the day          model  176.9 L   baseline  237.2 L   diff -25.4%   wins 7/12
```

Identical to the decimal.

**Investigation.** The probe borrowed the shipped builder for the "absolute tick" arm — and the shipped builder *is* the within-day builder, because the fix had already landed. The comparison had quietly become meaningless, and it would have kept reporting a confident number for as long as anyone ran it.

**Fix.** The probe now writes the absolute-tick builder out by hand, so both arms are genuinely different:

```text
absolute tick (as first shipped)   model  189.2 L   baseline  179.8 L   diff  +5.2%   wins 5/12
tick within the day                model  132.2 L   baseline  179.8 L   diff -26.5%   wins 7/12
```

**Lesson.** The within-day feature is **26.5 % better** over the forecast horizon — where the absolute tick was actually *worse* than the rule. A probe that cannot fail is not evidence, and this one had stopped being evidence without anyone noticing. It was found by reading the probe's own output and seeing two identical rows, not by any test.

## 6. How a defect gets into this catalogue

A defect is included when it is described in one of the source documents above, or in the body of a `fix`/`revert`/`perf` commit. Every row names its source day. Where a regression test exists it is named as `file::test name` and was checked to exist in the repository; where none exists, the cell says `—` rather than naming a test that is not there.

The `Test that pins it` column is the honest answer to "would this fail again if the fix were reverted?".

| Pinning | Count |
|---|---:|
| A named regression test exists | 51 |
| Pinned only by a script, drill or setting | 1 |
| **No dedicated regression test** | **18** |
| **Total** | **70** |

The 18 without a dedicated regression test are B2, B4, B8, B12, B21, B22, B29, B30, B32, B33, B39, B41, B47, B48, B54, B61, B69 and B70. Their rows say `—` rather than naming a test that does not exist. That is the honest limit of the current suite, and it is the list to work from next.
