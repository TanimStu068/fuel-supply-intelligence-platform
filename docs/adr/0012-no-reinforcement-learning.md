# ADR 0012 — No reinforcement learning

**Status:** Accepted
**Date:** Day 3 of 7
**Deciders:** the team

---

## Context

The brief lists *"adaptive learning from feedback"* among the possible
capabilities, alongside forecasting, anomaly detection and optimization. It
does **not** require reinforcement learning, and it does not forbid it.

The case for RL is that fuel allocation is a sequential decision problem
under uncertainty, which is exactly what RL is for: the dispatcher repeatedly
chooses where to send fuel, observes the outcome, and improves.

The case against it is specific to this problem:

1. **The feedback loop is too slow.** An RL agent needs many episodes to
   learn. The policy comparison ran **240 ticks per run (2.5 simulated
   days)**. At that rate an agent would need thousands of runs to learn
   anything, and each run is minutes of wall-clock time.
2. **The policy has to be safe on its first action.** The platform's
   allocations are consequential and human-approved. A policy that learns by
   trial and error would try bad allocations before it knew better, and every
   one of those is a real shipment in the simulated world.
3. **The simulator's total supply is 25 % below its total demand.** Service
   level cannot approach 1.0 in either run. The comparison is between two
   policies, not against a perfect score — so the reward function would have
   no clean ceiling to learn toward.
4. **The evaluation must be paced to the platform's own sync cycle.**
   Stepping the simulator flat out lets the world run away from the
   platform, and the resulting service level measures the step rate rather
   than the policy: **0.763 unpaced against 0.882 paced** for the same code.
   RL needs many episodes, and every episode needs pacing.

## Decision

**No reinforcement learning. The adaptive behaviour is a supervised forecast
plus a deterministic optimizer, and the learning loop is a retrain against a
held-out split.**

The adaptive loop that does exist:

```
observed demand → training rows → refit → held-out one-step comparison
                                      ↓
                              beats the rule?
                                      ↓
                              use it, or fall back
```

This is a genuine learning loop — the model's parameters change with the
data, and whether the change is kept is decided by measurement rather than by
assumption — but it is supervised and it is gated on evidence
([ADR 0006](0006-gate-model-on-held-out-one-step-comparison.md)).

## Alternatives considered

| Alternative | Why not |
|---|---|
| **Contextual bandit over stations** | Cheaper than full RL and it would learn *which* station to favour. But the reward is delayed — a dispatch is judged on whether the station stocked out hours later — and the bandit would have to learn from a signal that arrives long after the action. |
| **Full RL with a shaped reward** | The reward function would encode the policy's priorities by hand, which means the policy is written by a human and the learning only tunes the weights. It also needs the episode count the pacing constraint forbids, and every exploratory action is a real shipment. |
| **Offline RL on logged decisions** | The platform's decision history exists, but it was generated by the rule-based and model-driven policies. Learning from it would learn to imitate the current policies, with no way to exceed them. |
| **A bandit with an optimistic-exploration guard** | Still explores, and exploration still means bad allocations in the world. It also conflicts with the human-approval gate: an exploring agent's action is by definition one a human has not seen before. |
| **Keep the supervised model, add a wider policy search** | Rejected for the same reason the greedy policy was: the Day 4 log records that *"the greedy policy can spend a depot's allowance on the wrong station"* and states the limitation in the module docstring rather than hiding it. The optimizer orders by urgency, which mitigates it. |

## Consequences

**Good.** The platform's behaviour is **explainable** — every recommendation
carries its rationale, its signals, its constraints and its alternatives, and
the judge can read why the fuel went where it went. An RL policy's rationale
is a post-hoc explanation of a learned function.

**Good.** The learned component is **evaluable against a fixed benchmark**. The
held-out comparison gives a number that can be re-checked on every retrain,
which is what made the gate in ADR 0006 possible at all.

**Good.** Nothing exploratory reaches the world. Every allocation is either
rule-based, model-driven, or one of the two behind a human approval.

**Good.** The platform is **cheap to run and to reproduce**. There is no
training run to schedule, no episode count to budget, and no randomness in
the learning loop that would make two runs incomparable.

**Bad.** The platform does **not** learn the *policy*. It learns the demand
model and then applies a fixed, hand-written optimizer. In a world where the
right dispatch order depended on something outside the demand model, the
platform would not adapt. The Day 4 risk table names it: *"The greedy policy
can spend a depot's allowance on the wrong station → A later, more urgent
station may get nothing."*

**Bad.** The optimizer's ordering is fixed by urgency. There is no search
over alternative allocations — the platform produces one recommendation per
station/fuel, with alternatives recorded as context rather than evaluated.

**Bad.** Because the learning loop is supervised and gated, the platform's
adaptation is **bounded by what the features capture**. The features are
tick-within-day, hour, region and observed multipliers. A demand shift
outside those features would not be learned.

**Bad.** The evaluation's pacing requirement (§4 above) applies to RL too, so
the decision not to use RL does not remove the constraint — it only means the
constraint applies to the evaluation of two fixed policies rather than to a
learning run.
